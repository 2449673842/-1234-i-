## 第一部分：AI 编程修改与质量保障守则

为保证多人协作模式下代码的绝对安全与稳定性，AI 助手在进行任何代码修改前，必须无条件执行本部分守则。

### 1. 底线红线 (Red Lines & Zero Guessing)
* **禁止用猜测代替源码证据**：没读过源码，禁止判断根因；未查完调用链，禁止修改函数。**严禁在代码中编造或猜想项目中不存在的接口、变量、状态、Props 或文件**。
* **证据等级控制 (Evidence Levels)**：E0/E1 级（无证据或只有孤立代码但未查调用链）决不允许改代码。必须达到 **E3 级**（源码证据 + 全调用链分析 + 本地复现路径）才可执行修改。修复完后必须通过四维回归，达到 **E5 级**才可汇报完成。
* **多系统/引擎防御隔离**：改动某一平台或引擎（如 Python/Matplotlib）功能时，必须对不受支持的路径（如 R/ggplot2 路径）进行防御性隔离，防止单侧修改破坏全局兼容性。

### 2. 强制执行流程 (Mandatory Workflow)
在编写任何代码前，AI 必须优先输出 **前置预检 (Preflight)** 报告：
```md
# Preflight
1. 我理解的任务：
2. 我不会修改的内容（锁定范围）：
3. 我必须先读取的源码（列出待分析文件/函数）：
4. 我已有的证据（引用的源码行数）：
5. 我还缺的证据：
6. 孤立调用链排查（列出受影响的全部调用方）：
7. 是否具备修改条件：是/否
```
在执行修改的过程中，必须严格走完 **六阶段执行法 (Six-Phase Workflow)**：
* **A. 任务边界确认**：明确成功与失败标准，禁止顺手重构无关代码。
* **B. 源码证据收集**：以表格形式详列证据编号、文件、函数位置、支撑结论。
* **C. 问题确认与反证**：主动尝试寻找推翻当前假设的代码，确认非其他原因导致。
* **D. 影响面分析**：列出受影响的子系统并分析原因。
* **E. 最小修复方案**：遵循 `最小正确修复 > 局部重构 > 全局重构` 原则，提供兼容与回滚策略。
* **F. 实现与验证**：提供测试输出，指出未验证项和潜在遗留风险。

### 3. 全量引用追踪与孤立检测 (Reference Enforcement)
* 在修改任何组件、方法、接口定义或核心字段前，必须运行全局检索排查其在项目中的**所有调用方**。
* 必须在一次修改中，将声明处与所有调用处全部同步更新，严禁遗漏任何孤立的旧调用。

### 4. 属性访问“先证后写”约束 (Property & Schema Proof)
* 在编写任何涉及对象属性访问、解构、数据库增删改查的代码前，必须在设计文档中**先贴出该对象在源码中的 TypeScript 接口（Interface）定义或数据库 Schema 定义**，从源头上杜绝因“脑补属性”导致的运行时 Undefined 报错。

### 5. API 契约双向对照与沙箱测试 (API Contract & Sandbox Test)
* 涉及前后端交互逻辑时，必须列出前端 Request 与后端路由接收的字段对照。
* 修改代码后，必须通过独立的测试脚本（如在 `scratch/` 下模拟 HTTP 真实调用）进行请求，捕获真实的 HTTP Response 日志，证明前后端通路在运行时已经畅通。

### 6. 四维验证指标 (Validation Matrix)
任何功能改动宣称“完成”前，必须在本地执行并输出以下四重验证结果，拒绝口头断言：
1. **静态类型**：`npx tsc --noEmit` 零错误。
2. **单元测试**：前端及后端单元测试全部 PASS。
3. **接口契约**：接口冒烟测试全部 PASS。
4. **前端 E2E**：运行相关 UI 冒烟测试全部 PASS。

## 第二部分：系统性能与运行效率升级路线 (P0-P3)

### 1. P0 级别（崩溃与资源泄漏防御）
* **P0-1：Python/R 子进程取消传播**
  * **问题**：前端取消渲染请求后，后台子进程未被 kill，导致堆积。
  * **修复**：监听 Express `req.on('aborted')` 和 `close` 事件，强制调用 `child.kill('SIGKILL')` 释放资源。
* **P0-2：图表并发渲染上限控制**
  * **问题**：多请求并发时，服务器瞬间 spawn 数十个 Python/R 进程导致死机。
  * **修复**：引入信号量机制，设定 `MAX_CONCURRENT_RENDERS = 3`，超出时排队等待。
* **P0-3：CSV 数据内存缓存**
  * **问题**：每次 patch 操作都需要从磁盘重新读取解析大体积 CSV。
  * **修复**：建立内存 `Map<filePath, {rows, mtime}>`，根据文件修改时间（mtime）进行失效和缓存读取。
* **P0-4：渲染缓存 (render_cache) 自动淘汰**
  * **问题**：缓存数据无限膨胀导致 SQLite 数据库体积失控。
  * **修复**：在每次写入后进行 TTL/容量淘汰，仅保留最新 500 条数据。

### 2. P1 级别（体验瓶颈优化）
* **P1-1：数据库索引建设**
  * 在 `project_figures` 表上对 `(project_id, figure_index)` 建立联合索引，消除全表扫描。
* **P1-2：项目子图加载 N+1 查询优化**
  * 将项目加载时循环查询单个 session 的逻辑，改为 `WHERE id IN (?, ?, ...)` 批量获取，将 DB 查询次数从 N+1 降到 2。
* **P1-3：减少 `figSession` 的 useMemo 频繁重建**
  * 收窄依赖数组，将全局 `datasets` 及 `projectDrafts` 改为只订阅当前激活子图的片段，减少 60% 以上的前端组件无效重渲染。
* **P1-4：前端拖拽布局强制计算节流**
  * 使用 `requestAnimationFrame` 对 `updateOverlayGeometry` 进行节流控制，消除拖动鼠标时的 Layout Thrashing（布局抖动）。

### 3. P2/P3 级别（长效重构）
* **R 渲染回放优化**：预构建 `PROP_MAP` 字典，将 `latest_value()` 从 O(N³) 的线性扫描降低到 O(1) 的字典查找。
* **sessionStorage 序列化降噪**：序列化时剔除大型 SVG 字符串，并在写入时使用 `requestIdleCallback` 延迟，避免阻塞渲染主线程。

## 第三部分：多租户隔离与独立存储架构设计

为了实现用户隐私的绝对隔离，项目计划从“单租户”过渡到“多用户专属隔离存储”架构。

### 1. Database-Per-User（独立数据库设计）
* **全局共享数据库 (`data/global.db`)**：仅包含 `users`, `auth_sessions`, `subscriptions`, `redeem_codes` 等全局公共数据。
* **用户专属数据库 (`data/users/:userId/db/user.db`)**：每个用户拥有独立的文件系统目录。其下存储该用户专属的 `projects`, `export_assets`, `render_cache` 表。
* **优势**：物理隔离，彻底杜绝越权漏洞；用户注销直接删除该用户目录，天然符合隐私合规；避免全局数据库并发写入锁冲突。

### 2. 存储路径隔离
* 所有数据集上传、临时计算文件、导出资产和缩略图，一律重定向至用户专属子树：
  `data/users/:userId/projects/:projectId/files/`
* 使用严格的防目录越权拦截器，对所有 `userId` 和 `projectId` 过滤 `..` 及特殊斜杠，防止路径穿越攻击。

### 3. 自定义脚本沙箱执行
* 运行用户自定义 Python/R 脚本时，必须隔离在 Docker 容器或轻量级微VM中。
* 禁用网络访问，只读挂载用户数据目录，并施加内存（最高 256MB）与 CPU（最大 0.5 核）的强资源配额，防止拒绝服务攻击 (DoS)。

## 第四部分：安全防御与反爬虫策略

针对公网可能面临的恶意爬取与流量攻击，设计以下防线：

### 1. 资源接口 Token 校验
* 对导出的矢量资产 `/api/export-assets/:id` 启用严格的权限校验。
* 对直接引用的外链或临时下载，使用基于 HMAC 签名的动态 Token，Token 有效期设为 60 秒，过期即失效，防止批量下载。

### 2. API 异常频次检测与蜜罐封禁
* 对 `/api/export-assets` 接口进行速率监测。如果单账号在 5 分钟内请求下载超过 50 次，自动临时冻结其导出权限。
* 在前端 API 扫描路径中埋入隐藏的蜜罐接口（正常用户不可见）。一旦该接口收到请求，判定为爬虫扫描，立即封禁其 IP 与账号。

### 3. SVG 矢量追踪水印
* 在所有导出的 SVG 矢量文件中，自动注入带有加密签名的 `<metadata>` 信息（包含 `userId`, `assetId`, `timestamp` 的加密哈希）。若资产泄露或被非法倒卖，可通过元数据直接进行源头追溯。

## 第五部分：金融级（支付宝级）数据安全标准

### 1. 静态数据信封加密 (Envelope Encryption)
* 用户的 `user.db` 数据库使用 **SQLCipher** (AES-256 级别透明数据加密) 进行存储。
* 用户上传的原始 CSV 数据及高精度的导出文件采用**信封加密**：使用独立的 AES-GCM 数据密钥（DEK）加密文件；再将 DEK 通过云端硬件安全模块 (HSM/KMS) 的主密钥进行二次加密存储。

### 2. 块链式防篡改审计日志 (WORM Logs)
* 系统所有敏感变更（图表修改、脚本更新、资产导出、权限变动）均写入只写（WORM）审计日志表。
* 审计日志条目采用区块链式的哈希链连接：
  `Hash_N = SHA-256(Action + Timestamp + UserID + Hash_N-1)`
* 任何数据库层面的物理修改或删除都会导致哈希链断裂，立即触发安全警报并向独立日志服务器发送警报邮件。

### 3. 传输层安全 (TLS 1.3 Preload)
* 彻底禁用 TLS 1.0/1.1/1.2，仅支持 **TLS 1.3** 顶配安全通道。
* 启用 HSTS Preload，将域名提交至各大浏览器内核的预加载列表，防止协议降级攻击与中间人拦截。
